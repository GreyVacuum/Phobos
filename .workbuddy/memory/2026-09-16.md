## 移植 PR #118 的 CrateType extension（Phobos develop）

### 结论
已实现「自定义 crate 类型」功能，**未直接套用 PR diff**（该分支严重污染：包含 `.editorconfig` 缩进风格回退、`Phobos.vcxproj` 回退到 v141_xp 工具集、RadSite/Script/Shield 等无关文件的回退），而是**以 PR 为设计蓝本、在现有扩展框架上重写**。

### 采纳的关键决策
- **删除 PR 的 `DEFINE_LJMP(0x56BFC2, 0x56BFC7)`**（用户确认）。该 LJMP 实际是抹掉 `cmp edx,14h; jz 0x56BFFF` 这个 vanilla 守卫，会让**功能未启用时也改变原版随机箱行为**；而自定义箱类型号必然 > 20，本就通过该守卫并命中 `0x56BFF9`，所以 LJMP 对本功能**多余**。
- **不采用 PR 的「强制 n6=7 + 劫持 Darkness 分支」手法**。IDA 发现更干净的接管点 `0x481DCD`（`mov byte ptr [esp+1Bh], 0`，5 字节完整指令，位于 `RemoveCrate` 之后、效果 switch 分派之前，`ESI` 仍为 `CellClass*`）。因此**不依赖 `[Powerups]` 表、不需要改写水域检查、不需要 vanilla powerup 槽位被配置**。
- **反脏数据双条件判定**：`CellExt::CustomCrateIndex >= 0` **且** `OverlayData == 20`。因 `MapClass::RemoveCrate` 会把 `OverlayData` 清零，故「自定义箱过期后同格刷新箱」不可能同时满足两条件。

## 追加：补齐 Trigger Action 108 与 Crate.Chance（同日）

### 关键逆向结论
- **Trigger Action 108 = "Create Crate"**（Phobos 文档 `New-or-Enhanced-Logics.md:3455` 已这么称呼），处理函数是 **`TActionClass::CrateAtWP` @ `0x6E38B0`**。
- `CrateAtWP` 读 **`TActionClass::Value`（偏移 `0x90`）** 作为箱类型，直接传给 `MapClass::PlacePowerupCrate`（`push [esi+90h]` + `push <cell>` + `call 0x56BEC0`）。`TActionClass::Waypoint` = `+0x44`。
- `TActionClass::GetMode(108)` **无 case 0x6C → 返回 0**；`TActionClass::LoadFromINI`(`0x6DD5B0`) 的 `case 0` 会把 INI 的整数参数写进 `Value`(0x90)。
  ⇒ **动作 108 的参数本来就是整数、本来就被当箱类型用** → **自定义箱通过动作 108 无需任何新代码**，`CrateType=21+` 直接生效。且即使没有我的 hook，25+ 的非法值也只是退化成随机箱（`OverlayData >= 19` → 走随机 roll），不会崩。
- **发现并修掉上一版的运行时缺陷**：`MapClass::RemoveCrate` 在普通游戏里走 `SessionClass::Instance(0xA8B238) != 0` 的「Crates[] 查找」分支 → `sub_4A1750` → `sub_4A1AA0`，后者会把 **`CellClass::OverlayData`(0x11E) 清 0**。该调用发生在 `0x481D97`，**早于**我原来的接管点 `0x481DCD`。所以「`OverlayData == 20`」判定在实际运行时必然为假 → 功能全程失效（编译通过但逻辑死）。**修法：把识别提前到 `0x481ACE`**（也正是 vanilla 读 `OverlayData` 的位置），用文件级 static 暂存，再在 `0x481DCD` 消费。
- 别的有用常量：`Unsorted::Crates` = `0xA8B261`；`[Powerups]` 概率表 = `0x81DA8C`（19 个 int，0x81DA8C..0x81DAD4）；powerup 动画表 = `0x81DAD8`；water-allowed 表 = `0x89ECC0`（`byte[]`）。
- **`NoEffectPowerup = 18`（Pod）**：效果 switch 的跳转表只覆盖 0..17（`0x481DCA: cmp ebx,11h` / `0x481DD6: ja default`），18 落到 default ⇒ **对箱效果是空操作**。用它来「压住」vanilla 效果，这样就不需要 PR 那种「强制 n6=7 劫持 Darkness 分支」的载体 hack。

### Crate.Chance 的语义选择
- 随机箱的类型是在**采集时**由 `CollectCrate` 内的加权 roll 决定（`0x481AD3` 起，用 `[Powerups]` 概率表）——`MapClass::PlaceRandomCrate`(`0x56BD40`) 只调 `sub_4A17C0` 建外观+挂计时器，**根本不设定类型**。
- 因此把 `Crate.Chance` 实现为**与 vanilla `[Powerups]` 同量纲的相对权重（int）**：在 `0x481ACE` 对「`OverlayData >= 19` 即原版会 roll 类型的箱」做一次合并加权抽取（复用 `GeneralUtils::ChooseOneWeighted`）。命中 vanilla 索引就设 EBX=该索引（用我这张表取代 vanilla 的 roll），命中自定义就记状态并把 EBX 设为 18（压制 vanilla 效果）。`Crate.Chance` 默认 0 ⇒ 没有任何类型配置时**完全走原逻辑**。

### 最终 hook 表（6 处，全部逐字节验证过指令边界）
| 用途 | 地址 | size | 偷取指令 |
|---|---|---|---|
| `PlacePowerupCrate` 记录自定义箱 | `0x56BFF9` | 6 | `mov [eax+11Eh], dl` |
| `CollectCrate` 识别 + `Crate.Chance` 注入 | `0x481ACE` | 5 | `cmp bl,13h; jb 0x481B1C` |
| `CollectCrate` 水域检查豁免 | `0x481D5B` | 6 | `mov al,[ebx+89ECC0h]` |
| `CollectCrate` 接管应用 | `0x481DCD` | 5 | `mov byte [esp+1Bh], 0` |
| 单位 `CarriesCrate` | `0x73844A` | 6 | 跨指令，但该 hook 永不返回 0 |
| 建筑 `CrateBeneath` | `0x442215` | 7 | `mov ecx,[esp+10h]; push 14h; push ecx` |

水域 hook 特意选在 `mov al,[ebx+89ECC0h]` 而不是它前面的 `cmp`：这样**不依赖「偷取字节回放后的 flags 传递」**（其后 `test al,al` 自己重设 flags）。同理 `0x481ACE` 的 `jb` 在偷取字节内部，也不依赖外部 flags。

## 追加 2：INI 接口重设计（用户要求"重做，去掉大量副作用"）

用户判定 PR 那套 INI 副作用太多，要求重新设计。**新增 hook 数不变（仍 6 个），只换接口与 dispatch。**

### 被判定为副作用的设计（PR 原样继承的）
1. `Crate.Type=1..6` **魔法整数**互斥单选 —— 必须查文档；一个箱只能做一件事。
2. **静默忽略**（最严重）：`Crate.Type=5` 时设了 `Crate.Weapon` 也不生效，无任何提示。
3. `CrateType=21+下标` —— **差一陷阱**：`[CrateTypes] 0=NAME` 对应 `CrateType=21`，极易写错且错得很隐蔽。
4. `Crate.SuperWeaponGrant` 用 bool 表达两条不同行为（`false` 的含义反直觉）。
5. `Crate.AllowWater=false` 会**隐式送钱**（读 `Rules->SoloCrateMoney`），用户无法控制。
6. 效果失败（如 SW 未配、Units 为空）也**隐式送钱**。
7. `Crate.Chance` 是 int 权重、**与 vanilla `[Powerups]` 数值同量纲** —— 换一个 rulesmd 后同一个数值含义完全变了。
8. `Crate.Type=6` 全员治疗**无任何目标过滤**。

### 新设计原则
- **数据驱动，无 master switch**：删掉 `Crate.Type`。**每个键独立生效**，设了就执行，可任意组合 ⇒ 结构上不可能有"死键"。
  （代价：未设任何效果键的箱"只播反馈"；已加载入期 warning 点名。）
- **全名称引用，无数字**：`CrateType=` 接受 `[CrateTypes]` 名、vanilla `[Powerups]` 名（19 个：`Money / Unit / HealBase / Cloak / Explosion / Napalm / Squad / Darkness / Reveal / Armor / Speed / Firepower / ICBM / Invulnerability / Veteran / IonStorm / Gas / Tiberium / Pod`）或 `Random`；留空=原版行为。无法解析 → `Debug::INIParseFailed` **显式报错**，绝不静默退化。内部仍用 `21+index` 传递，但**用户永不可见** ⇒ 差一陷阱消失。
- **不设隐式兜底**：删掉"失败送钱"；`Crate.CollectOnWater=false` 改为**箱子留在原地不采集**（原版盒一直返回 true，故用 `return 0x483389` 跳过 RemoveCrate 实现"留箱"）。
- **`Crate.Chance` 改为概率（double 0.0–1.0，支持 `%`）**：语义 = "拾取时 roll 类型的箱成为本类型的概率"。求和 `S`：`S<=0` **完全不掷骰、零 RNG 影响**；否则先按 `min(S,1)` 门控、再在自定义类型内按权重归一化抽取 ⇒ **与 vanilla 权重表量纲解耦**。
- 治疗改为 `Crate.HealTargets`（复用 Phobos 的 `AffectedHouse` 过滤器，`EnumFunctions::CanTargetHouse`）+ `Crate.HealWarhead`。
- 其他新键：`Crate.Units.Count`、`Crate.SuperWeaponFire`（真名为"就地发射"，非 bool-as-mode）、`Crate.Money.Min/.Max`（`Nullable` ⇒ 未设=不给钱，且 Max 单独设也生效）。
- **载入期 lint**：无任何效果键 / 设了 `SuperWeaponFire` 无 `SuperWeapon` / 设了 `HealWarhead` 无 `HealTargets` / 设了 `Units.Count` 无 `Units` / `Chance` 越界 → 全部 `Debug::Log` 点名，并 clamp `Chance`。

### 顺手清理的技术债
- 新常量全部改用 **`YRpp/Powerups.h` 的现成访问器**：`Powerups::Weights`(0x81DA8C)、`Powerups::Naval`(0x89ECC0)、`Powerups::Anims`(0x81DAD8)、`Powerups::Arguments`(0x89EC28)、`Powerups::Effects`(0x7E523C 名字表)。之前我手工硬编码的地址**全部作废**。
- `PowerupCount = std::size(Powerups::Effects)`，并加 `static_assert` 锁定 `19` 与 `NoEffectPowerup == 18`。
- 新增 `src/New/Type/CrateSource.h`（纯常量 + `Parse`/`GetCustomType` 声明，仅前置声明 `CrateTypeClass`）⇒ 让 `Ext/TechnoType/Body.h` 不必依赖整个 `CrateTypeClass`。
- 修掉一处自审发现的逻辑漏洞：**概率注入出来的自定义箱原先没检查 `CollectOnWater`**（只有显式放置的检查了），已在注入分支补上。

## 追加 3：用户报"SuperWeapon 不正常" → 全量副作用审计（IDA 实证）

用户反馈 `Crate` 对 SuperWeapon 行为异常，并要求全面排查副作用。逐条反编译核对后**确认 12 处真实缺陷**（其中 7 处在 SW 路径）。

### SuperClass 三个入口的真实语义（0x6CB560 / 0x6CC390 / 0x6CB920，全部反编译确认）
- **`SuperClass::Grant(oneTime, announce, onHold)` @0x6CB560**：`if (!IsPresent)` 守卫；`*(BYTE*)(this+0x6E) = oneTime`（即 `IsOneTime`）；`*(BYTE*)(this+0x6D) = 1`（`IsPresent`）。函数尾部 `if (a4 && IsPresent) {...}` 之后有 **`if (!IsOneTime) return a2;`** ⇒ **非一次性授予时 `announce` 参数根本不可达**（永远不播公告）。
- **`SuperClass::Launch(double@ST0, CellStruct*, isPlayer)` @0x6CC390**：按 `Type->Type`（`SuperWeaponType` 枚举 0..11）switch；**每个 case 开头都是 `if (*(BYTE*)(this+0x6F))` = `if (IsReady)`** ⇒ 未充能时**整段什么都不做**。`default: return` ⇒ **引擎未知种类（Ares 自定义超武）静默无操作**。且 Launch **不消耗充能**（不清 `IsReady`、不重置计时器）。`case 3`(ChronoSphere) 会写 `this+0x62`(`ChronoMapCoords`)；`case 4`(ChronoWarp) **读**它当传送起点 ⇒ 没有先前施法就是垃圾坐标。
- **`SuperClass::ClickFire(double@ST0, CellStruct*, isPlayer)` @0x6CB920**：要求 `IsReady`（`(ChronoMapCoords==-1 || !IsPresent || !IsReady) && !ManualControl → return 0`），通过后调 `Launch`，**然后清 `IsReady` 并重置充能计时器** ⇒ 这才是"正常开火"。但 `ChronoMapCoords==-1` 时直接拒发且无法从返回值区分。
- **致命点**：`Launch`/`ClickFire` 的真实签名**各有一个 x87 的 `double`（ST0）参数**，而 **YRpp 只声明了 `(cell, isPlayer)`** ⇒ 从 DLL 调用时 ST0 是垃圾（Nuke 的 `case 0` 拿它算 payload 弹道）。
- **`SuperClass::SetReadiness(bool)` @0x6CB820** = 只写一个字节 `this[111]`，**不碰计时器/侧边栏**。
- **`SuperClass::SetCharge(pct)` @0x6CC1E0**：`if (!IsPresent) return;` → `v5 = rechargeTime - round(pct*0.01*rechargeTime)`；`if (!v5) IsReady = 1;` 并写 `this+48/52/56` ⇒ **同时置 ready 与写入充能计时器** ✓ 这才是"充满"的正确 API。

### 结论：取消自动发射模式
**`Fire` 模式彻底删除**（仅保留 `Grant` / `Charge`），理由已写进头文件注释与文档：x87 参数不可提供、未知种类静默失败、ChronoWarp 依赖先前状态、`ChronoMapCoords==-1` 会拒发 ⇒ 自动发射"对部分超武有效、对另一部分静默失败"，正是要消灭的那类副作用。PR 也自认这是它的已知问题重灾区。**"在箱格自动开火"改由 `Crate.Weapon=` 承担**（走正常武器/弹道路径，可靠）✓

### 本轮修掉的 12 处副作用
1. `Grant(true,…)` **永久**把超武标记为一次性(`IsOneTime`) → 改 `Grant(false, false, false)`。
2. 超武已存在时 `Grant` **静默返回 0** → 先查 `IsPresent` 并显式记日志。
3. `Launch` 在未充能时**静默无效**（常态）→ 相关调用删除。
4. `Launch` 不消耗充能 ⇒ 白送一发 → 删除。
5. `Launch` 对未知种类 `default: return` 静默无操作 → 删除。
6. `Launch`/`ClickFire` 未建模的 x87 参数（ST0 垃圾）→ 不调用。
7. 非一次性授予时 `announce` 不可达（原代码传 `true` 有误导性）→ 传 `false` 并说明。
8. EVA 用 `IsControlledByHuman()` 门控 ⇒ 多人下**每个真人客户端的玩家**都会听到（含 AI/他人采集）→ 改 `pHouse->IsCurrentPlayer()`。
9. EVA 用 `VoxClass::PlayAtPos`（定位音、全局）→ 改 Phobos 自己的惯例 `VoxClass::PlayIndex`（`Ext/Building/Hooks.Selling.cpp` 同款）。
10. 生成的单位 `QueueMission(Guard, true)` 后**又** `NextMission()` ⇒ 可能立刻跳过 Guard → 删掉 `NextMission()`（Phobos 惯例见 `Ext/Unit/Body.cpp:183`、`Ext/Script/Hooks.cpp:40`）。
11. `RecheckTechTree = true` 在**一个单位都没生成**时也置位 → 改为仅 `spawned > 0` 时。
12. 治疗用正序 range-for 遍历 `TechnoClass::Array` 同时调 `ReceiveDamage`（元素可能被移除 ⇒ `end()` 快照失效）→ 改**倒序索引**遍历。

### 复核确认无问题（无需改）

### 解法
- 新增 `addSuperWeaponToSidebar()`：`if (pHouse->IsCurrentPlayer()) SidebarClass::Instance.AddCameo(AbstractType::Special, superIndex)` + `RepaintSidebar(GetObjectTabIdx(...))`（侧栏属于本机玩家，故只对 `IsCurrentPlayer` 的阵营做）。三条动作路径（Grant / OneTime / Charge 里授予时）都调用它。
- `Crate.SuperWeaponAction` 改为三态：**`Charge`（默认，先授予再 `SetCharge(100)`）/ `Grant`（永久，可充能）/ `OneTime`（原版箱行为，一次性）**。`Grant`/`OneTime` 都会先查 `IsPresent`，已有则记日志不做事；`Grant` 返回 false 也记日志 —— 全程无静默。

### `Crate.TypeID`（用户提案，采纳）
- 新增 **`Crate.TypeID`（必填，≥21）**，成为 crate 类型的**唯一引用标识**：`CrateType=` 键、以及**地图触发器动作 108 的参数**都用它。低于 21 会与 vanilla 箱索引冲突 → 报错并 `Reset()`。
- **关键简化**：因为 TypeID 天然 ≥21、vanilla 索引 ≤20，**两者永不冲突 ⇒ 内部不再需要任何偏移编码**。`PlacePowerupCrate` 收到的原始 powerup 值**就是 TypeID**，`0x56BFF9` hook 直接 `GetByTypeID(powerup)` 解析 ⇒ 触发器路径与 techno 路径**完全同构**。
- `CrateSource` 精简为 `Default=-1 / Random=20（=引擎自身哨兵）/ Invalid=-2 / FirstTypeID=21`；`Parse` 依次尝试：`[CrateTypes]` 名 → `random` → **数字**（≥21 当 TypeID，0..20 当 vanilla 索引）→ `[Powerups]` 名；全部失败 → `INIParseFailed`。
- `CellExt::CustomCrateIndex`（数组下标）**改名为 `CustomCrateTypeID`（存 TypeID）** —— 列表重排或存档跨版本都不会指错。
- 无 `TypeID` 的 crate 类型**无法被任何东西选中**，故：载入期报错；`Crate.Chance` 掷骰时权重按 0 处理；重复 TypeID 报错（后加载者报）。

## 追加 5：新增「一次性但需等待」超武 + 2 个新效果，并处置原版 4 个哑效果

用户要求：①`Crate.SuperWeaponAction` 加一个"一次性但需要等待时间"的；②继续扩展箱子效果，并指出原版 `Squad / Invulnerability / IonStorm / Pod` **四个是哑的（不可用）**。

### ① 一次性但需等待 → 正交键，而非第 4 个枚举值
新键 **`Crate.SuperWeaponStartsReady`（bool，默认 true）**：为 `false` 时 `Grant`/`OneTime` 授予后调用 **`SetCharge(0)`**。
- 实证依据 `SuperClass::SetCharge(pct)`（0x6CC1E0）：`v5 = RechargeTime - round(pct*0.01*RechargeTime)`，`if (!v5) IsReady = 1;` ⇒ **`SetCharge(0)` 把计时器置满且不置 `IsReady`** = "从零开始充能" ✓
- 所以 `Action=OneTime` + `StartsReady=false` = 用户要的"一次性但需等待" ✓；且该键与 `Grant` 正交组合出"永久但起始为空" ✓ 比加第 4 个枚举值表达力更强。
- `Action=Charge` 时该键无意义（Charge 本来就置 100）⇒ 载入期显式报告该矛盾组合 ✓

### ② 原版 4 个哑效果的处置（逐个实证）
- **Squad(6)** —— 引擎无独立概念。**已可用 `Crate.Units` + `Crate.Units.Count=N` 表达**（从列表随机抽 N 个）⇒ 无需新代码，仅文档化。

- **Pod(18)** —— Phobos 的 `DroppodTypeClass` 是**数据类**（`DropPod.*` 挂在 TechnoType 上），真正投送由 **`DropPodLocomotionClass`** 驱动（`DroppodTypeClass.cpp:138` 那段是**飞行中**逻辑，不是"生成一个舱"的入口）；引擎/Ares 的 `Droppod` SW 才会把单位放进该 locomotion ⇒ 箱子**无法可靠启动真投送**。处置：用 `Crate.Units` + `Crate.Anim`（填投送舱的 Puff/GroundAnim）做外观等同效果 ⇒ 文档化，不写半成品。
